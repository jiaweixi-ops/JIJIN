# V1.3 Operational Alerting

V1.3 Phase 7 adds a deterministic operational alert layer around the forward-simulation system. Alerts are observations about account/data/accounting state; they are **not** AI recommendations and never approve, submit, cancel, or modify an order.

## Lifecycle

Each condition has one stable `dedupe_key` and one durable `OperationalAlert` row:

```text
condition appears
  -> OPEN
  -> optional Feishu notification
  -> human ADMIN acknowledgement -> ACKNOWLEDGED
  -> underlying deterministic condition disappears -> RESOLVED
  -> same condition later reappears -> OPEN + occurrence_count increment
```

Acknowledgement only records human awareness. It never resolves the underlying condition. Resolution is automatic and only occurs when the next deterministic sweep no longer detects the condition.

## Detected conditions

Phase 7 initially covers:

- `SOFT_RESERVED_CASH_EXCEEDS_AVAILABLE` — CRITICAL
- `MISSING_CONFIRMED_NAV` — HIGH
- `DRAWDOWN_LIMIT_REACHED` — HIGH
- `LOSS_STREAK_LIMIT_REACHED` — HIGH
- `RECONCILIATION_BLOCKING` — CRITICAL
- `FORMAL_SNAPSHOT_PENDING` — WARN after 23:00 local time on an open CN trading day when a held-account still lacks the exact-NAV daily snapshot

Portfolio alerts reuse the same deterministic `PortfolioRiskDashboardService` state that feeds risk visibility. Reconciliation alerts come from unresolved blocking diffs. Formal snapshot alerts never fabricate P&L with stale NAV.

## Scheduler and delivery

`operational_alerts` runs every 30 minutes from 08:00 through 23:30 in the configured business timezone, including weekends. Calendar-specific conditions still enforce the relevant trading calendar.

The sweep is safe to repeat. A unique `dedupe_key` prevents duplicate lifecycle rows. Only `OPEN` alerts with `notified_at IS NULL` are eligible for initial Feishu delivery. If delivery fails, the alert remains pending and can be retried by a later sweep. If no Feishu webhook is configured, no notification timestamp is written.

## API

All endpoints require internal authentication:

```text
GET  /operations/alerts
POST /operations/alerts/sweep
POST /operations/alerts/{alert_id}/ack
```

`GET /operations/alerts` supports optional `state`, `severity`, `scope_id`, and bounded `limit` filters.

Manual sweep requires system or ADMIN. Acknowledgement requires an authenticated human ADMIN credential; the shared system service token cannot impersonate a human acknowledgement.

## Operational semantics

- Drawdown or loss-streak alerts do **not** block SELL risk reduction. They reflect the same rule that prevents expanding BUY risk while allowing reduction.
- `RECONCILIATION_BLOCKING` corresponds to the existing hard trade freeze until blocking diffs are resolved.
- `MISSING_CONFIRMED_NAV` means portfolio valuation is incomplete. Research may still exist, but deterministic BUY risk evaluation remains fail-closed where valuation is required.
- `FORMAL_SNAPSHOT_PENDING` means the exact-NAV daily snapshot is absent after the expected window. QDII/FOF timing can legitimately cause this; the system waits rather than substituting an old or estimated NAV.

## Audit

Lifecycle transitions create `AuditLog` records:

```text
operations.alert.open
operations.alert.reopen
operations.alert.acknowledge
operations.alert.resolve
operations.alert.notified
```

The alert row preserves first/last seen timestamps, occurrence count, acknowledgement identity/time, notification time, resolved time, severity and deterministic details used to explain the condition.
