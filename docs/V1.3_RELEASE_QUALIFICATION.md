# V1.3 Phase 10 — Release Qualification

V1.3.0 RC uses two separate gates. The engineering gate can be completed immediately in an isolated CI/runtime rehearsal. The field gate is based only on elapsed, persisted forward-simulation evidence and therefore cannot be accelerated or manually overridden in production.

## Release states

- `ENGINEERING_READY`: current schema/runtime invariants pass and the Phase 10 deterministic CI matrix is green.
- `FIELD_OBSERVATION_PENDING`: engineering is ready, but the real observation window and/or release-blocking operational defects have not cleared.
- `RELEASE_READY`: every enabled simulation account has enough formal forward observations and no release blocker remains.

There is intentionally no API or database field that lets an operator force `RELEASE_READY`.

## Engineering qualification

Run after `alembic upgrade head`:

```bash
python scripts/release_qualification.py engineering
```

The runtime check is non-destructive and verifies:

- database schema equals the code's Alembic head;
- `LIVE_TRADING_ENABLED=false`;
- no unsupported historical `CONVERT` orders are present;
- no confirmed NAV is dated in the future;
- simulation cash buckets are non-negative;
- release-gate thresholds are fixed at 30 natural days and 20 business-day formal snapshots per enabled simulation account;
- no manual stable-release override exists.

The CI `qualification-rehearsal` job additionally runs the deterministic failure/replay matrix across existing subsystem tests: Feishu replay/idempotency, operational scheduler replay, alert lifecycle, real fund-data conflicts, reconciliation/finalization, AI/research failure handling, and simulation settlement/NAV behavior. Fresh SQLite/PostgreSQL migrations and hardened-container checks remain separate mandatory CI jobs.

## Field observation gate

The field window starts from the **first persisted `ENGINEERING_READY` run for the current release + suite version**. It does not reuse old pre-RC snapshots.

For `RELEASE_READY`, all of the following must be true at the same evaluation:

1. At least **30 natural days** have elapsed in the inclusive observation window.
2. Every enabled simulation account has at least **20 distinct formal `PortfolioSnapshot` dates** that are open CN business days and are on/after the engineering epoch.
3. No active release-blocking operational alert remains. The release-blocking alert types are `SOFT_RESERVED_CASH_EXCEEDS_AVAILABLE`, `MISSING_CONFIRMED_NAV`, and `RECONCILIATION_BLOCKING`.
4. No unresolved blocking reconciliation diff remains for enabled simulation accounts.
5. No `FAILED` operational run remains in the observation window.
6. No decision review whose horizon has matured remains unresolved.
7. Live trading remains disabled.

`DRAWDOWN_LIMIT_REACHED` and `LOSS_STREAK_LIMIT_REACHED` are genuine market/risk states, not software release defects, so they remain visible risk alerts but do not block a stable software release. Likewise, `PARTIAL` operational runs may represent a transient non-critical delivery failure such as a Feishu card error after deterministic business work completed; a historical `PARTIAL` row therefore does not permanently poison a fixed field epoch. True `FAILED` runs remain blockers.

The gate uses formal `PortfolioSnapshot` rows, which are created only from exact confirmed-NAV accounting. Estimated/provisional/PENDING NAV cannot create observation credit.

Check without persisting:

```text
GET /qualification/status
```

Persist an audited run (system/ADMIN only):

```text
POST /qualification/engineering
POST /qualification/field-gate
```

Inspect history:

```text
GET /qualification/runs
```

Operator CLI:

```bash
python scripts/release_qualification.py field
python scripts/release_qualification.py scheduled
```

`field`/`scheduled` return a non-zero code while the real field window is pending. This is intentional and prevents CI/operator scripts from treating a not-yet-observed release as stable.

## Accelerated 20-business-day rehearsal vs. real observation

The test suite creates a synthetic 30-day window containing exactly 20 open business-day formal snapshots and proves the gate passes only at 20/30. It also proves the gate fails at 19 business days, 29 calendar days, an active release-blocking alert, an unresolved blocking reconciliation difference, a failed operational run, or live-trading enablement. Separate tests prove that a normal HIGH drawdown alert and a transient `PARTIAL` Feishu-delivery run do not falsely block an otherwise clean release.

That synthetic test validates the gate logic; it **does not claim that 30 real days have passed**. V1.3 remains `1.3.0rc1` until the server-derived field gate reaches `RELEASE_READY` with real forward-simulation evidence.

## Nightly qualification

At 23:55 in the configured timezone the scheduler persists a qualification run. If no `ENGINEERING_READY` epoch exists for the current release/suite, it first runs the engineering gate. Once the engineering epoch exists, subsequent nightly checks evaluate the real field gate. This creates an auditable record of the observation window without letting the scheduler bypass any release condition.

## Hard boundaries

- No standalone backtest center is introduced.
- Historical data is not substituted for the field observation window.
- No future/estimated/provisional NAV is accepted as formal release evidence.
- No AI score, report, or qualification result changes prompts, strategy parameters, risk limits, model routing, or order state automatically.
- No qualification action enables live trading.
- Stable `1.3.0` is not declared or tagged until the real field gate actually reaches `RELEASE_READY`.
