# V1.3 RC Field Operations Runbook

V1.3 `1.3.0rc1` is an engineering-complete forward-simulation release candidate. This runbook covers the real field-observation period that must complete before a stable `1.3.0` declaration.

The field period is **not** a backtest. Historical data, synthetic snapshots and accelerated CI fixtures never count as real elapsed release evidence.

## Release boundary

The field deployment keeps these invariants permanently enabled:

- `LIVE_TRADING_ENABLED=false`;
- simulation accounts only;
- DeepSeek remains the only CIO/final decision model;
- Kimi/Qwen cannot replace an unavailable CIO;
- Research Pipeline creates at most `SUGGESTED` candidates;
- Operational Orchestrator advances at most to `PENDING_CONFIRM`;
- human confirmation remains required;
- exact confirmed NAV is required for formal settlement/snapshots;
- DataQuality RED fails closed;
- no prompt/strategy/risk/model-routing mutation is automatic.

## 1. Deployment target

Formal field observation is intended to run on a persistent host with PostgreSQL. SQLite remains useful for tests and local development but is deliberately rejected by the field-operation preflight.

Recommended host properties:

- stable 24x7 Docker host;
- persistent local disk with sufficient PostgreSQL space;
- outbound HTTPS access for registered data sources and AI providers;
- host clock synchronized with NTP;
- `TIMEZONE=Asia/Shanghai` for the current CN-market RC;
- loopback-only API binding retained unless a controlled TLS/VPN reverse proxy is added.

Start from the hardened compose configuration:

```bash
cp .env.compose.example .env
# Fill every secret/configuration value before starting.
docker compose up --build -d
```

Verify:

```bash
docker compose ps
curl http://127.0.0.1:${JIJIN_API_PORT:-8000}/health
curl http://127.0.0.1:${JIJIN_API_PORT:-8000}/ready
```

`/ready` must be healthy and the database must be on the current Alembic head.

## 2. Required RC configuration

The field preflight treats the following as blocking requirements:

- `APP_ENV=prod` or `staging`;
- PostgreSQL database backend;
- current Alembic schema / engineering qualification ready;
- at least one enabled simulation account;
- at least one enabled real fund-data connector;
- at least one enabled registered research source;
- DeepSeek API key + model;
- Qwen API key + model;
- Kimi API key + model.

Feishu being disabled is reported as a warning rather than a release-gate override because the API can still be operated manually; however, the intended RC exercise should enable Feishu so human confirmation, delivery and alert paths are actually covered.

Run the preflight from the application environment:

```bash
python scripts/field_operations.py preflight
```

Exit code `0` means the deployment requirements are ready. Exit code `2` means one or more field-deployment blockers remain. The command never changes orders or release status.

Read-only API equivalent:

```text
GET /field-operations/status
```

The response includes deployment blockers/warnings, configured data/AI inventory, engineering/field qualification progress, today's operational jobs, active alerts, and latest formal snapshot date for each enabled simulation account.

## 3. Real data bootstrap

Before starting the observation epoch, configure the real fund universe deliberately. A small controlled universe is preferred for the first RC.

For each tracked fund:

1. create/verify the fund profile and platform rules;
2. register the authoritative `DataSource`;
3. register an enabled `FundDataConnector`;
4. ingest fund trading rules and confirmed NAV observations;
5. register explicit research collection sources for the target account/fund;
6. verify DataQuality is not RED before expecting an executable candidate;
7. verify fees, cutoff time, share class, calendar and confirmation-day rules.

Do not hard-code GREEN or inject fake confirmed NAV merely to make the field run progress.

## 4. Start the real observation epoch

After preflight is clean, run:

```bash
python scripts/release_qualification.py engineering
```

The persisted result must be:

```text
ENGINEERING_READY
blocker_count = 0
```

The first persisted `ENGINEERING_READY` for the current release/suite becomes the observation epoch. Do not delete/recreate that record to make the clock appear older.

The application installs a nightly `release_qualification` scheduler job at **23:55 Asia/Shanghai**, every day. It journals the field gate without requiring an operator to remember to run it.

## 5. Daily RC workflow

The normal automated path is:

```text
07:45  fund data premarket sync
08:15  research collection
08:45  morning brief
12:45  research collection refresh
13:00  multi-source dossier
13:10  predecision fund-data refresh
13:15  Kimi -> Qwen -> DeepSeek CIO pipeline
13:30  early-cutoff processing
14:00  normal decision window
18:00  post-close fund-data sync
20:30  month-end probe
22:15  pre-snapshot fund-data sync
22:30  exact-NAV portfolio snapshot
23:00  operational alert sweep continues
23:15  late fund-data sync
23:30  exact-NAV snapshot retry
23:35  forward decision review refresh
23:50  management reports
23:55  release qualification journal
```

The 13:10 fund-data refresh intentionally runs **before** the 13:15 Research Pipeline. That keeps trading rules/NAV observations fresh when `DataQualityGate` performs its pre-model fail-closed check instead of making the AI path rely on the 07:45 observation.

Cash settlement and alert sweeps continue on their existing shorter schedules.

A missing QDII/FOF exact NAV is allowed to delay a formal snapshot. The system must wait rather than reuse an old or estimated NAV as formal evidence.

## 6. What counts toward stable release

Stable `1.3.0` requires one simultaneous server-derived result with:

- at least **30 real natural days** since the RC engineering epoch;
- at least **20 distinct formal CN business-day `PortfolioSnapshot` dates** for every enabled simulation account;
- no release-blocking accounting/data-integrity operational alerts;
- no unresolved blocking reconciliation diff;
- no failed operational run in the observation window;
- no matured unresolved decision review;
- live trading still disabled.

Check progress at any time:

```bash
python scripts/field_operations.py status
python scripts/release_qualification.py field
```

The first command is informational. The second persists an audited field-gate run and intentionally exits non-zero while the real observation window is incomplete.

## 7. Bug-fix discipline during the observation window

During the 30-day window:

Allowed without changing investment intent:

- crash fixes;
- timezone/serialization fixes;
- parsing and connector reliability fixes;
- authentication/security fixes;
- duplicate callback/idempotency fixes;
- accounting/reconciliation correctness fixes;
- alerting/observability fixes.

Do not silently change:

- strategy logic;
- risk limits;
- prompts;
- AI role ownership;
- model routing;
- valuation semantics;
- order approval/submission boundary.

A material behavioral change should increment the qualification suite/release boundary and begin a fresh observation epoch rather than pretending the old evidence still certifies the new behavior.

## 8. PostgreSQL backup and restore drill

A field RC is not qualified merely because the service runs. The database must be recoverable.

Create a logical backup from the compose PostgreSQL container:

```bash
mkdir -p backups
set -a
. ./.env
set +a

docker compose exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc \
  > "backups/jijin-$(date +%Y%m%d-%H%M%S).dump"
```

Keep backups outside the PostgreSQL data volume and protect them like application data/secrets.

### Restore drill: use a throwaway database

Do **not** test restore by overwriting the active field database. Create a temporary database inside the same PostgreSQL instance or, preferably, an isolated PostgreSQL container/host:

```bash
set -a
. ./.env
set +a

TEST_DB=jijin_restore_drill

docker compose exec -T postgres createdb -U "$POSTGRES_USER" "$TEST_DB"
cat backups/<backup-file>.dump | docker compose exec -T postgres \
  pg_restore -U "$POSTGRES_USER" -d "$TEST_DB" --clean --if-exists
```

Then verify at minimum:

- expected application tables exist;
- `alembic_version` equals the current code head;
- recent `release_qualification_run`, `portfolio_snapshot`, `orders`, reconciliation and audit records are present;
- row counts are plausible;
- no restore error is ignored.

Drop the throwaway database after verification:

```bash
docker compose exec -T postgres dropdb -U "$POSTGRES_USER" "$TEST_DB"
```

Record the drill date, backup file checksum, restore target, result and operator in the external operations log. Backup presence without a successful restore drill is not sufficient evidence.

## 9. Daily operator checklist

Once per business day review:

- `/ready` is healthy;
- `GET /field-operations/status` has no new deployment blockers;
- DataQuality RED changes are understood;
- today's required operational jobs are not `FAILED`;
- HIGH/CRITICAL alerts are explained/resolved;
- expected formal snapshot exists when exact NAV should be available;
- reconciliation has no unresolved blocking diff;
- AI quota/cost has not unexpectedly spiked;
- Feishu confirmation and alert delivery are working if enabled;
- release qualification progress advances only from real persisted evidence.

## 10. Stable promotion

Do not rename the build to stable merely because CI is green. When `GET /qualification/status` reports:

```text
field.status = RELEASE_READY
stable_release_ready = true
```

perform one final read-only acceptance, take a fresh PostgreSQL backup, execute/record a restore drill, confirm `main` CI is green, then change `1.3.0rc1 -> 1.3.0` and create the stable release/tag.

Until then the correct version remains `1.3.0rc1`.
