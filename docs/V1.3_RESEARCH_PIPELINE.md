# V1.3 Research Pipeline — 可信研究材料到模拟候选单

## 目标与边界

Phase 2 只解决一件事：把**已经进入系统的可信研究材料**转换为可审计、可恢复、可幂等的模拟候选订单。

```text
可信材料 Inbox
  -> Kimi 研究整理
  -> Qwen 结构化与冲突标记
  -> Evidence 持久化
  -> DeepSeek CIO
  -> DecisionPlan
  -> SUGGESTED BUY/SELL Order
  -> 13:30 / 14:00 Phase-1 编排器
  -> Python DataQuality + Risk
  -> PENDING_CONFIRM
  -> 真人确认
```

Phase 2 **不**自动抓全网、不自动批准、不自动提交 SimulationBroker、不支持 CONVERT、不接真钱交易。DeepSeek CIO 不可用时不会切换到其他模型代替 CIO。

## 状态机

`research_inbox.status`：

- `NEW`：已摄入，等待处理。
- `PROCESSING`：某个 worker 已通过条件更新取得处理权。
- `PROCESSED`：研究流水线完成；可能生成 0 或 1 个 `SUGGESTED` 候选单。终态，重复 process 直接返回原结果。
- `BLOCKED`：数据质量 RED 或 CIO unavailable 等 fail-closed 情形；不生成候选单。自动调度不会无限重试，修复外部条件后可人工重新 process。
- `FAILED`：模型输出、来源校验、Schema、订单映射等发生确定性或暂时性错误；自动调度可在次数上限内重试。

`PROCESSING` 超过 `RESEARCH_PROCESSING_STALE_MINUTES` 可被重新接管，防止进程崩溃永久卡住。自动失败重试受 `RESEARCH_PIPELINE_MAX_ATTEMPTS` 限制。

## Inbox 幂等

创建请求必须提供 `idempotency_key`。数据库唯一边界是：

```text
(account_id, idempotency_key)
```

系统同时计算完整规范化请求的 SHA-256 `payload_hash`：

- 同一个 key + 同一 payload：返回原条目，不重复摄入。
- 同一个 key + 不同 payload：409 / `ResearchIdempotencyConflict`，绝不静默覆盖。

每份 material 额外保存 `content_sha256`，用于审计材料在进入模型前是否发生变化。

## 可信来源绑定

API 摄入的 material 至少包含：

- `source_name`
- 可选 `source_url`
- `published_at`
- `observed_at`
- `content`

系统不会因为 Kimi/Qwen 声称某条证据“来自某网站”就直接相信。Qwen 结构化输出进入 `research_evidence` 前必须通过来源绑定：

- 有 `source_url` 的 evidence，其 URL 必须精确存在于当前 inbox 的 material URL 集合；
- 没有 URL 的 evidence，其 `source_name` 必须存在于当前 material source_name 集合；
- `evidence_id` 在同一 research item 内必须唯一；
- observed/published 时间不得位于不合理的未来。

来源不匹配会使 item 进入 `FAILED`，不会产生候选订单。

## 分阶段持久化与恢复

流水线不是“一次函数调用全成全败”。每个昂贵阶段完成后会保存结果：

1. `research_packet` — Kimi 输出；
2. `structured_packet` + `research_evidence` — Qwen 输出；
3. `decision_plan` — DeepSeek CIO 输出；
4. `candidate_order_ids` — 映射后的候选单。

发生暂时失败后，重试会复用已经落库的前序阶段，避免无意义重复调用模型和重复计费。

## DataQuality fail-closed

开始模型调用前先运行服务端 `DataQualityGate`：

- RED：不调用 Kimi/Qwen/DeepSeek；记录质量快照，生成 WAIT 语义并将 item 标记 `BLOCKED`。
- GREEN/YELLOW：允许进入研究阶段，但后续候选单仍要经过 Phase-1 的 Python RiskService。

`settlement_eligibility` 与 `research_quality` 仍是两个维度。研究允许并不等于可结算。

## CIO 不可用

DeepSeek 调用失败由既有 `DecisionEngine` 转为：

```text
WAIT + abstain_reason=CIO_UNAVAILABLE
```

ResearchPipeline 随后将条目标记为 `BLOCKED`，不生成订单。不会由 Kimi/Qwen 接替 CIO。

## DecisionPlan -> Order 映射

Phase 2 的映射规则比模型输出更严格：

- 仅允许 BUY / SELL；CONVERT 直接拒绝。
- 一个 fund-scoped research item 最多生成一个交易候选。
- `action.fund_code` 必须等于 inbox 对应 Fund.code。
- BUY/SELL 必须引用已经持久化的 evidence IDs。
- 订单幂等键由 `research_item_id + decision_id + action` 的稳定摘要生成。
- 新订单状态只能是 `SUGGESTED`。
- 不调用 RiskService，不自动进入 `PENDING_CONFIRM`，更不会 APPROVE/SUBMIT。

订单的 `data_snapshot` 保存 research item、payload hash、pipeline version、decision id/as_of、evidence IDs 和 DataQuality 快照，后续 Phase-1 风控采用合并写入，不会覆盖这些字段。

## API

所有 `/research/*` API 都要求内部认证。

修改类操作只允许：

- system principal；
- `EDITOR`；
- `ADMIN`。

主要入口：

```text
POST /research/inbox
GET  /research/inbox
GET  /research/inbox/{item_id}
GET  /research/inbox/{item_id}/evidence
POST /research/inbox/{item_id}/process
```

列表接口默认不返回完整 material content，详情接口才返回，降低无意泄露大段研究材料的概率。

## 自动调度

工作日 13:15：

```text
NEW / 可重试 FAILED
 -> ResearchPipelineService.process_pending()
 -> SUGGESTED candidates
```

随后复用 Phase 1：

- 13:30 提前截止基金进入风控；
- 14:00 其余候选进入风控；
- 风控通过最多推进到 `PENDING_CONFIRM` 并发送飞书卡片。

自动流水线始终停在真人确认之前。

```text
RESEARCH_PIPELINE_BATCH_SIZE=5
RESEARCH_PIPELINE_MAX_ATTEMPTS=5
```

研究材料仍受：

```text
AI_MAX_OUTPUT_TOKENS
AI_DAILY_MAX_CALLS_PER_SUBJECT
AI_DAILY_MAX_ESTIMATED_COST
```

控制。AI cost/usage 规则沿用 V1.2.2 hardening。

## 验收标准

Phase 2 至少满足：

1. 同 key 同 payload 重放不产生第二条 Inbox；异 payload 409。
2. RED DataQuality 在任何 AI 调用前阻断。
3. Qwen/模型伪造未摄入来源时失败且不产生 evidence/order。
4. Evidence 持久化后，BUY/SELL 只能引用这些 evidence IDs。
5. 一条 research item 最多产生一个 SUGGESTED 交易候选。
6. 重放已完成 item 不产生重复订单。
7. DeepSeek CIO 不可用时 WAIT/BLOCKED，无替代 CIO。
8. 自动调度仅生成候选；13:30/14:00 才执行确定性风控；绝不自动批准。
9. SQLite/PostgreSQL `alembic upgrade head` 均成功。
10. Ruff、compileall、pytest、container-hardening 全绿。
