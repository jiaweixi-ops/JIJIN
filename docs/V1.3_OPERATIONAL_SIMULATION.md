# V1.3 Operational Simulation — Phase 1

## 目标

V1.3 的第一阶段把 V1.2.2 中仅打印日志的定时任务升级为**可执行、可审计、可幂等重放边界明确**的日常模拟盘编排。

它仍然不是实盘系统。任何 BUY/SELL 候选最多自动推进到 `PENDING_CONFIRM`，必须由真实用户确认后才能进入 SimulationBroker；不会自动审批、不会自动提交、更不会连接真钱账户。

## 每日编排

默认时区继续使用 `TIMEZONE`（默认 `Asia/Shanghai`）。APScheduler 只负责触发，交易日判断在业务层再次执行。

| 时间 | Job | Phase 1 行为 |
| --- | --- | --- |
| 08:45 | `morning_brief` | 过期候选清理、全基金 DataQuality 汇总、每个启用模拟账户的资产/现金/昨日与累计盈亏简报；配置 Webhook 时发送飞书卡片 |
| 13:30 | `early_cutoff` | 找出安全确认窗口不晚于 14:00 的基金，发送提前截止提醒，并优先对这些基金已有候选单执行风控与卡片发送 |
| 14:00 | `decision_window` | 对数据库中已有的 BUY/SELL 候选单执行 server-side DataQuality + RiskService；通过后进入 `PENDING_CONFIRM` 并发送交易卡；拒绝则进入 `RISK_REJECTED` |
| 20:30 | `month_end_probe` | 仅在当月最后一个 CN 交易日生成月末报告；存在 APPROVED/SUBMITTED/IN_TRANSIT/PARTIALLY_CONFIRMED 时保持 `PROVISIONAL` |
| 08:00–22:59 / 15min | `settle_due_cash` | 保留 V1.2.2 已接通的赎回在途现金到期结转 |

### 14:00 的明确边界

`decision_window` **不会自己编造研究材料，也不会把“没有 AI 输入”伪装成 CIO 结论**。Phase 1 只消费已经持久化成 `Order(status=SUGGESTED/MODIFIED/EXECUTION_FAILED)` 的 BUY/SELL 候选。

后续 Phase 2 再把“可信研究输入 → Kimi → Qwen → DeepSeek → 候选 Order”接到该队列前面。这样可以先证明日常业务编排、截止时间、风控、飞书、人审链稳定，再接自动研究生成，避免把多个故障域一次性混在一起。

## OperationalRun

新增 `operational_run` 表作为每日任务审计账本，唯一键为：

```text
(job_name, business_date)
```

主要字段：

- `trigger`: scheduler / manual
- `status`: RUNNING / SUCCEEDED / SKIPPED / PARTIAL / FAILED
- `attempt`
- `scheduled_for` / `started_at` / `finished_at`
- `summary` JSON
- `error`

`SUCCEEDED`、`SKIPPED`、`PARTIAL` 都是终态，同一业务日不会再次自动产生副作用。`FAILED` 可由后续触发重试。`RUNNING` 超过 `OPERATIONAL_RUN_STALE_MINUTES`（默认 30 分钟）后允许被新实例接管，避免进程崩溃后永久卡死。

> 该唯一键解决的是“每日 job 不重复执行”的业务幂等边界，不替代订单自身的 idempotency/version/状态机控制。

## 候选订单推进

13:30 / 14:00 对候选单采用统一流程：

```text
SUGGESTED / MODIFIED / EXECUTION_FAILED
    ↓
检查 expires_at
    ↓
DataQualityGate.evaluate_fund()
    ↓
SEND_TO_RISK
    ↓
RiskService.check()
    ├─ fail → RISK_REJECTED
    └─ pass → PENDING_CONFIRM → Feishu trade card
```

写入订单的 `data_snapshot` / `risk_snapshot` 包含：

- research quality
- settlement eligibility
- quality reasons
- hard blocks / warnings
- lot allocation
- emergency confirmation requirement
- penalty fee snapshot
- checked/captured timestamp
- `source=operational_orchestrator`

系统主体可以执行风控编排，但不能代替真实用户完成批准。

## 提前截止规则

Phase 1 把 14:00 作为正常决策窗口，把：

```text
fund.cut_off_time - DEFAULT_CUTOFF_BUFFER_MINUTES <= 14:00
```

定义为 early-cutoff fund。

因此例如默认 buffer=10 分钟时，14:10 或更早截止的基金不会等待正常 14:00 流程；13:30 job 会先提示并处理已有候选。

## 手工运行与审计

新增：

```text
GET  /operations/runs
POST /operations/run/{job_name}
```

`GET` 允许已认证内部主体查看运行记录；手工触发只允许 system principal 或 ADMIN。

支持的 job_name：

- `morning_brief`
- `early_cutoff`
- `decision_window`
- `month_end_probe`

手工触发仍受 `(job_name, business_date)` 幂等约束，不是绕过幂等的“强制重跑”按钮。

## 数据库迁移

新增 Alembic revision：

```text
20260912_02
    ↓
20260913_01  operational_run
```

切换到 V1.3 分支后必须先：

```bash
alembic upgrade head
```

## Phase 1 验收标准

1. 非交易日四个日常 job 均可审计地 `SKIPPED`，不是仅依赖 cron 周一到周五。
2. 同一 job / business date 重复触发不会重复发送卡片或重复推进订单。
3. 早截止候选可在 13:30 进入风险流程，不等待 14:00。
4. 14:00 候选通过风控后最多到 `PENDING_CONFIRM`，绝不自动批准。
5. DataQuality RED、适当性失败、现金不足、对账 blocking diff 等仍由原 RiskService 硬阻断。
6. 飞书发送失败不会回滚已完成的确定性风控状态；运行记录进入 `PARTIAL` 并保留错误。
7. SQLite / PostgreSQL 都能从 Alembic head 正常创建 `operational_run`。
8. 现有 V1.2.2 回归测试继续全绿。

## Phase 2

下一阶段再实现：

```text
可信研究材料 Inbox
    ↓
Kimi research
    ↓
Qwen structure
    ↓
DeepSeek CIO
    ↓
DecisionPlan → candidate Order
    ↓

```

研究材料必须有来源、时间戳、基金/主题绑定和新鲜度，不能让 scheduler 直接把网络碎片拼成交易结论。
